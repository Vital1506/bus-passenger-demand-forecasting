Operator planning assumptions

Enter planned trips per day and a target boardings-per-trip threshold for each route. The table shows point / upper-approximate scenarios for the forecast peak day. Trips at target are simple daily averages divided by your threshold; they are not timetable recommendations, occupancy estimates, or peak-load forecasts. The historical error range is approximate, and values are saved in this browser only. Export includes the forecast rows and these local assumptions.

Waiting for service

This page checks the connected service every 60 seconds while open. New daily counts update forecasts after ingestion and model refresh.

Scheduled daily-count feed

An approved company scheduler can send route-day counts to POST /api/data/ingest with the bearer key. Matching route and service-date rows are safely replaced, and the current model refreshes the forecast. New rows do not retrain the model automatically; schedule training separately.

Example integration request
POST /api/data/ingest
Authorization: Bearer <operator-key>
Content-Type: application/json

{
  "source_system": "ticketing_daily_export",
  "records": [
    {"service_date": "2026-11-09", "route_id": "R10", "passengers": 1240}
  ]
}

Live telemetry needs a separate adapter

This endpoint accepts daily counts. It does not connect to ticketing or AVL/GTFS-Realtime systems by itself. A company-approved integration must map the source feed, define its schedule, and persist data safely.

Time-based evaluation

Model quality is compared with a same-weekday seasonal-naive baseline using historical validation. Lower WAPE is better; it does not guarantee future accuracy.

What this score means

WAPE is total absolute forecast error divided by total observed boardings across backtest periods. Compare scores across the same dates and data definition.

Before operational use

Validate with your service calendar, disruptions, route changes, and a shadow run. Forecast intervals are approximate historical error ranges.
